# 📘 СПЕЦИФИКАЦИЯ ПРИЛОЖЕНИЯ: ПСИХИАТРИЧЕСКИЙ МОНИТОРИНГ (MVP)

## 1. Общие положения
- **Домен:** Строго психиатрия/психотерапия. Универсализация не предусмотрена на этапе MVP.
- **Назначение:** Инструмент межвизитного мониторинга, а не система экстренной помощи или клинического принятия решений.
- **Ключевые метрики успеха:**
  1. Экономия времени врача на приёме
  2. Быстрое визуальное понимание динамики терапии
  3. Точное отслеживание побочных эффектов (ПЭ)
  4. Снижение количества упущенных деталей
  5. Повышение комплаенса пациента
  6. Упрощение анализа связей: доза → эффект → переносимость

---

## 2. Роли, аутентификация и онбординг

### 👨‍⚕️ Врач
- **Регистрация:** Email + пароль. Поле `email_verified` по умолчанию `false`. Верификация и загрузка документов → отложено.
- **Функции:** Создание пациентов, назначение диагнозов, выбор шкал/тестов, установка частоты прохождения тестов и оценки ПЭ, просмотр дашборда и графиков.
- **Данные врача:** Не влияет на логику расчётов в MVP. Только профильные метаданные.

### 🧑‍🤝‍🧑 Пациент
- **Создание:** Врач генерирует `temp_login` и `temp_password`. Передаёт офлайн/в мессенджере. Отправка приглашений на почту в MVP отключена.
- **Первый вход:** Ввод временных данных → опциональная привязка почты и смена пароля.
- **Онбординг (мягкий):**
  - Обязательно: прохождение ≥1 стартового теста + указание списка текущих препаратов (МНН/бренд, доза, кратность).
  - Даты старта/доз: допускается `«не помню точно»`, `«примерно»`, `«месяц/год»`, `«диапазон»`.
  - Нет жёсткой блокировки. Незаполненные поля помечаются статусом `incomplete` с подсказками.
- **Права:** Указывает фактический приём препаратов, проходит тесты, фиксирует ПЭ. Не может менять диагнозы.

## 3. Ядро логики (Бизнес-правила)

### 🎨 Цветовая индикация карточек пациентов
Приоритет строгой иерархии: **ПЭ > Клиническая динамика**.
Логика пересчитывается при любом изменении данных.

| Цвет | Условие (логическое ИЛИ для 🟡/🔴, И для 🟢) |
|------|-----------------------------------------------|
| 🔴 **Красный** | ≥1 ПЭ тяжёлой степени (UKU 3-4) **ИЛИ** отрицательная клиническая динамика |
| 🟡 **Жёлтый** | >3 ПЭ лёгкой степени (UKU 1) **ИЛИ** ≥1 ПЭ средней степени (UKU 2) **ИЛИ** отсутствие ожидаемой положительной динамики к контрольной точке |
| 🟢 **Зелёный** | Положительная клиническая динамика **И** ≤3 ПЭ лёгкой степени **И** 0 ПЭ средней/тяжёлой степени |
| ⚪ **Серый** | Недостаточно данных (<7 дней терапии или отсутствуют результаты тестов) |

### 📅 Контрольные точки и клиническая динамика
- Источники: конфигурационная таблица `clinical_control_points`.
- Примеры (настраиваемые):
  - Депрессия / Тревога: 4–6 недель (критерий: снижение баллов ≥50% или ≥5 пунктов от базового)
  - ОКР: 8–12 недель
  - Мания: 1–2 недели
- **Алгоритм MVP:** 
  1. Фиксируется дата первого теста (`baseline_date`) и начальный балл.
  2. При достижении `baseline_date + control_point_days` система сравнивает текущий балл с базовым.
  3. Если улучшение `< критерия` → статус динамики `stable` или `worsened` → влияет на цвет карточки.
- **Множественные диагнозы:** Не смешиваются. Для каждого диагноза рассчитывается своя динамика по привязанной шкале. Визуально → вкладки/переключатель диагнозов.

### ⏱️ Лента событий (Event Timeline)
Критически важный слой. Все значимые изменения фиксируются с `timestamp`. Текущее состояние является проекцией из ленты.
- **Фиксируемые события:**
  - `drug_started`, `dose_changed`, `dose_skipped`, `drug_stopped`
  - `test_completed`, `se_reported_start`, `se_resolved`
  - `diagnosis_updated_by_doctor`, `monitoring_rule_changed`
- **Редактирование/Удаление:** Пациент может исправить или удалить запись о ПЭ. В ленте сохраняется исходная запись + запись `correction` с новым `timestamp`. История не перезаписывается.
- **Заполнение задним числом:** Запрещено. Фиксируется только фактическое время прохождения теста или изменения.

### 💊 Побочные эффекты (ПЭ)
- **Источник данных:** Справочник на базе UKU (код, название, система организма).
- **Ввод пациентом:**
  - Поиск по названию симптома (обязательно) + навигация по системам.
  - Выбор тяжести: `0` (нет) – `4` (очень тяжёлый).
  - Длительность: `<24ч` (указать примерное время начала/окончания) или `≥24ч`.
  - Гибкие даты: точная дата, диапазон, месяц, год, «примерно».
- **Интерпретация:** Пациент не обязан отличать ПЭ от симптома болезни. Всё, что он отмечает как проблему на терапии, сохраняется. Врач впоследствии классифицирует.
- **Частота оценки:** Врач выбирает конкретный ПЭ из списка активных → задаёт интервал (каждые N дней/по датам). Система создаёт повторяющуюся задачу для пациента.

## 4. Логика графиков и визуализации

| График | Ось X | Ось Y | Логика построения |
|--------|-------|-------|-------------------|
| **Препараты** | Календарные дни/недели | Доза (мг/ЕД) | Группировка по МНН. Цвет линии детерминирован по хэшу МНН. Точки соединяются линейно. Пропуски не интерполируются. |
| **Эффект терапии** | Календарные дни/недели | Баллы шкалы | Отдельный график на диагноз. Переключение вкладками. Показывает только итоговый балл (домены отложены). Направление улучшения зависит от шкалы (обычно ↓ = улучшение). |
| **Побочные эффекты** | Календарные дни/недели | Тяжесть (0–4 UKU) | Линия начинается с даты фиксации. При снижении тяжести до 0 или пометке «разрешился» линия обрывается. |

- **Оверлей (наложение графиков):** Отложен на финальную версию. В MVP графики независимы.
- **Синхронизация:** Все графики используют общую временную ось. Вертикальные маркеры событий (старт препарата, пропуск, оценка ПЭ) могут отображаться как пунктирные линии при наведении.

## 5. Интерфейсные потоки (Logical UX)

### 🖥️ Врач
1. **Дашборд:** Сетка/список карточек пациентов. Сортировка: 🔴 → 🟡 → 🟢 → ⚪. На карточке: ФИО, возраст, диагнозы, текущие препараты (снимок), дата последнего визита, главный симптом/ПЭ (ручная пометка).
2. **Детальная страница:**
   - Вверху: переключатель диагнозов.
   - Блок 1: График препаратов + список изменений с датами.
   - Блок 2: График эффекта (по выбранному диагнозу) + таблица результатов тестов.
   - Блок 3: График ПЭ + список активных ПЭ с датами.
   - Управление: `+ Назначить тест` (выбор шкалы, частота), `+ Частота оценки ПЭ`, блок `Цели терапии` (ручной чек-лист).
   - Снизу/сбоку: Хронологическая лента событий (`timeline`).

### 📱 Пациент
1. **Главный экран:** 3 модуля-плитки:
   - `Препараты`: список текущих, кнопка `Изменить`, `Добавить`, `Отметить пропуск`. Напоминания о приёме → опциональные in-app уведомления.
   - `Тесты`: список назначенных, индикатор просрочки, кнопка `Пройти`. После прохождения данные сразу уходят на сервер.
   - `Побочные эффекты`: поисковая строка + категории. Форма добавления: поиск → тяжесть → длительность → гибкая дата. Список назначенных повторных оценок ПЭ.
2. **Настройки:** Привязка почты, смена пароля, управление типами уведомлений (все/частично/выкл).

## 6. Границы MVP и отложенный функционал

| ✅ Входит в MVP | ❌ Отложено (V2/V3) |
|----------------|---------------------|
| Регистрация врача (email+pass) | Верификация документов, отправка приглашений на почту |
| Временный логин/пароль для пациента | Интеграция с МИС/ЭМК, мультидоменные шкалы |
| Мягкий онбординг, гибкие даты | Домены симптомов, вероятность отказа от терапии |
| Цветовая логика (ПЭ > динамика) | Сложная аналитика, предиктивные модели, наложение графиков |
| 3 графика (МНН, итоговые баллы, UKU) | Автоматические клинические выводы за врача |
| Лента событий с `timestamp` | Сценарий смены врача, экстренные алерты |
| Архивация неактивных (>90 дней) | Пуш-уведомления, email-рассылки |

## 7. Руководство для технической модели (что передать далее)

1. **Архитектура данных:** Реализовать через событийно-ориентированный подход. Текущее состояние (`current_state`) вычисляется из агрегации `event_log`. Это обеспечит корректную отрисовку графиков и аудит.
2. **Конфигурируемость:** Вынести в отдельные таблицы/файлы:
   - `scales_config` (название, диапазон баллов, направление улучшения, шкалы-сателлиты)
   - `clinical_rules` (диагноз → шкала → контрольная точка в днях → порог ответа)
   - `se_dictionary` (UKU коды, системные категории, локализованные названия)
3. **Обработка «грязных» данных:**
   - Пропущенные тесты не блокируют логику, просто оставляют пробелы в графиках.
   - Даты в формате `approx` хранятся как `start_date`, `end_date`, `precision_level` (`exact`, `month`, `year`, `range`). Графики игнорируют нечёткие точки или отображают их как маркеры с пометкой.
4. **Безопасность и изоляция:** Полная изоляция данных между пациентами одного врача. Диагнозы и правила мониторинга доступны только врачу. Пациент видит только свои назначенные задачи.
5. **Уведомления:** В MVP реализовать только in-app задачи (task queue). Флаг `notifications_enabled` на уровне пользователя. Серверный cron/jobs для проверки просроченных тестов и формирования списка задач.
6. **Масштабируемость логики цвета:** Вынести правила сравнения в конфигурационный модуль. При добавлении новых шкал или ПЭ цвет должен пересчитываться без изменения кода ядра.
