### [2026-05-17] — Extensible seeder module for reference data (`app/seeders/`)

**Status**: accepted

**Context**: `medications_reference` requires seed data to function (the medication typeahead returns nothing on a fresh DB). The initial implementation was a one-off `scripts/seed_medications.py` script: ad-hoc, not idempotent, and not wired into the deploy pipeline. As more reference tables arrive (ICD codes, side-effect categories, etc.) the ad-hoc approach would produce a proliferation of disconnected scripts.

**Decision**: replace the ad-hoc script with a structured seeder module at `app/seeders/`:

- `base.py` — `BaseSeeder` ABC with a single `async run(session) -> int` method
- one file per reference table (e.g. `medications.py`)
- `__init__.py` — `ALL_SEEDERS` list; execution order = list order
- `scripts/seed.py` — thin CLI wrapper (`--list`, `--seeder NAME`, `--dry-run`)
- `Makefile` targets: `make seed`, `make migrate-seed`

Each seeder uses `INSERT … ON CONFLICT DO NOTHING` (backed by a `UNIQUE` constraint on the natural key) so the command is fully idempotent and safe to run in CI/CD pipelines without state tracking.

**Alternatives considered**:
- Embed seed data directly in Alembic migrations — rejected: data and schema version independently; a data-only change would require a schema migration, and the `down_revision` chain would encode a business-data assumption into infrastructure history.
- Repeatable Alembic revisions (Flyway `R__` pattern) — not supported natively; would require a custom Alembic plugin.
- Application-startup auto-seed — rejected: mutates the DB on every cold start; fails loudly in read-only replicas; hides intent.

**Consequences**:
- (+) Adding a new reference table = one new file + one line in `ALL_SEEDERS`. No other changes.
- (+) `make migrate-seed` is the single standard command for any new environment (dev, staging, prod).
- (+) Fully idempotent — can be part of a CI smoke step.
- (−) Requires a `UNIQUE` constraint on the natural key of each reference table (enforced by migration; this is correct schema design anyway).

### [2026-05-17] — OpenAPI-first frontend types via `generate:api`

**Status**: accepted

**Context**: Phase 02 added patients, diagnoses, and medications. The initial implementation hand-wrote TypeScript interfaces in `frontend/app/shared/types/patients.ts` that duplicated the backend's Pydantic schemas. These drifted immediately: `dose_mg` was typed as `number | null` on the frontend but the backend serialises it as `string | null` (Decimal); `Partial<*Out>` was used as mutation input types instead of the dedicated `*Create`/`*Update` schemas the backend already exposes.

**Decision**: all frontend TypeScript types that mirror API contracts come exclusively from `frontend/app/shared/types/schema.ts`, which is generated by `openapi-typescript` from the live backend's `/openapi.json`. The script `frontend/scripts/generate-api.js` runs as `pnpm generate:api`. Running it is a named gate check in `STACK.md` and a named rule in `AGENTS.md`.

**Alternatives considered**:
- Keep hand-written types and enforce a review step — rejected because humans forget and the drift is silent until runtime.
- Use a shared `types/` package — premature for a monorepo of this size; `generate:api` achieves the same contract guarantee without the tooling overhead.

**Consequences**:
- (+) Frontend types are always in sync with the backend; mismatches surface as TypeScript errors before a PR is opened.
- (+) Mutation inputs use the correct `*Create`/`*Update` schemas, not overly-permissive `Partial<*Out>`.
- (−) `generate:api` requires the backend to be running (`docker compose up`); CI will need the backend available at schema-sync time.
